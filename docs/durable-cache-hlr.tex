\begin{requirement}{HLR-SCOPE.V1-03}[draft][stakeholderRequirement]{Fewest mechanisms, measured gains}

  \localreqdiagram*{hlr05}{\reqid}{\reqdesc}

  WHEN two or more alternatives each satisfy the requirements an architecture
  decision must meet, the decision shall adopt the alternative that requires
  this project to build the fewest mechanisms of its own --- counted as
  components, public interfaces, background tasks, and on-disk structures
  built rather than adopted --- unless an alternative with more mechanisms
  improves, by at least 20\,\%, a figure that a performance test case of this
  specification measures.

  The first functional version, released as 0.1.0, applied this rule without
  the exception: proven components doing the heavy lifting were preferred to
  bespoke ones, even at the cost of peak space or I/O efficiency, and the
  decisions taken that way stand. With that version working, the exception
  admits optimisations, but only measured ones. \emph{Improves} means raises
  a throughput or lowers a latency, as measured on the host and under the
  conditions the performance test case sets
  (\reqref{TC-PERFORMANCE.LOOKUP-01}, \reqref{TC-PERFORMANCE.HITRATE-01},
  \reqref{TC-PERFORMANCE.STORERATE-01}, \reqref{TC-PERFORMANCE.BURSTHITS-01});
  a gain no such test case measures, or one below 20\,\%, does not count.

  The requirement is verified by inspection --- each architecture decision
  record's \emph{Alternatives considered} section states what an alternative
  rejected on these grounds would have required the project to build, and a
  decision that takes the exception names the mechanisms it adds, the
  performance test case, and the figures measured for both alternatives.

  \reqdiaglink{overview}{\textit{View the domain overview.}}

  \reqexpect{satisfy}{ADR-PERSISTENCE.MECHANISM-01}{Adopt the storage substrate
  that requires this project to build the fewest mechanisms of its own, and
  state in its alternatives what each rejected substrate would have required
  building.}
  \reqexpect{satisfy}{ADR-OBSERVABILITY.METRICS-01}{Adopt the metrics mechanism
  that requires this project to build the fewest mechanisms of its own, and
  state in its alternatives what each rejected one would have required
  building.}
\end{requirement}

\begin{requirement}{HLR-PERSISTENCE.DURABLE-01}[draft][stakeholderRequirement]{Durable Persistence}

  \localreqdiagram*{hlr01}{\reqid}{\reqdesc}

  WHEN the cache process exits --- in an orderly way or by crashing --- the
  cache shall serve, from the process that starts next, every cached HTTP
  object whose storage had completed before the exit.

  A process exit leaves the host's own state intact; what the cache owes
  after the host itself crashes or loses power is stated separately in
  \reqref{HLR-PERSISTENCE.CRASHSAFE-02}, and the size of the cache it can
  hold in \reqref{HLR-PERSISTENCE.CAPACITY-01}.

  \reqdiaglink{overview}{\textit{View the domain overview.}}

  \reqexpect{satisfy}{ADR-PERSISTENCE.MECHANISM-01}{Establish the storage
  substrate and mechanism that persists cached objects across an exit of the
  cache process.}
  \reqexpect{verify}{TC-PERSISTENCE.RESTART-01}{Verify that every object whose
  storage completed before the cache process exited, in an orderly way or by
  crashing, is served by the process that starts next.}
\end{requirement}

\begin{requirement}{HLR-PERSISTENCE.CAPACITY-01}[draft][stakeholderRequirement]{Capacity beyond RAM}

\begin{requirement}{HLR-PERSISTENCE.CRASHSAFE-02}[draft][stakeholderRequirement]{Host-crash safety}

  \localreqdiagram*{hlr07}{\reqid}{\reqdesc}

  IF the cache's host crashes or loses power, THEN the cache, once running
  again, shall serve no object whose purge it had acknowledged before the
  crash, and no object whose content differs from what was stored --- the
  latter, where its integrator has configured it to store without waiting
  for the storage device and not to discard its content after a host
  restart, provided its file system records a file's length only once the
  file's data is written.

  Cached objects can be fetched again from their origin, so losing some of
  them in a host crash --- each then simply a cache miss --- is acceptable;
  serving wrong or purged content is not.

  Storing without waiting for the storage device is the configuration
  \reqref{HLR-PERFORMANCE.STORERATE-01} asks for. In it, a host crash can
  leave in place an object whose content never reached the device. A file
  system that records a file's length only once the file's data is written
  --- ext4 in its default \texttt{data=ordered} mode, XFS, btrfs --- then
  leaves the object short, which the cache detects; one that may record the
  length first, as ext4 does with \texttt{data=writeback}, can leave it at
  its full length, reading back as zeros, which the cache cannot detect. An
  integrator that chooses this configuration on a file system of the second
  kind accepts that risk, unless it also has the cache discard its content
  after a host restart (\reqref{ADR-PERSISTENCE.UNSYNCED-01}).

  This assumes a storage stack that honours flush requests --- what it
  acknowledges as flushed is on stable storage --- and that returns the data
  written to it or an error. Detecting data corrupted at rest, or lost by a
  device that acknowledges flushes it has not made, is the storage layer's
  responsibility, not the cache's.

  \reqdiaglink{overview}{\textit{View the domain overview.}}

  \reqexpect{satisfy}{ADR-PERSISTENCE.DURABILITY-02}{Decide which writes are
  synchronised to stable storage, and what integrity check detects the rest,
  so that a host crash can lose objects but never make the cache serve
  corrupted or purged content.}
  \reqexpect{verify}{TC-PERSISTENCE.CRASHSAFE-02}{Verify that, in every state a
  host crash or power loss can leave on disk, the restarted cache serves no
  object whose purge it had acknowledged and no object whose content differs
  from what was stored, in each configuration the requirement covers.}
\end{requirement}

\begin{requirement}{HLR-EFFICIENCY.SPACE-01}[draft][stakeholderRequirement]{Space Efficiency}

  \localreqdiagram*{hlr02}{\reqid}{\reqdesc}

  The cache shall hold the objects it caches in operation with an on-disk
  space overhead of no more than 25\,\% of those objects' own metadata and
  body bytes.

  The overhead is the storage the cache's directory tree occupies on disk ---
  allocated blocks, not file lengths --- minus the metadata and body bytes of
  the objects it holds, so it counts record headers, reserved headroom,
  block rounding, per-file and per-directory costs, and leftover files alike.
  It is measured over what the deployment actually caches, because overhead
  depends strongly on object sizes: a 500-byte object in a 4~KiB block carries
  roughly 700\,\% overhead, a 1~MiB object well under 1\,\%. The first
  functional version knowingly does not meet this requirement for workloads
  dominated by small objects: \reqref{ADR-EFFICIENCY.COMPACTION-01} defers the
  machinery that would, and declares the conflict.

  \reqdiaglink{overview}{\textit{View the domain overview.}}

  \reqexpect{deriveReqt}{REQ-EFFICIENCY.FRAGMENTATION-01}{Bound how the space
  the on-disk layout consumes beyond the objects' own bytes grows with the
  number of objects smaller than one file-system block, the share of the
  overhead a plain file system makes grow with the object count.}
  \reqexpect{verify}{TC-EFFICIENCY.SPACE-01}{Measure the on-disk space overhead
  as this requirement defines it, allocated blocks minus the objects' own
  metadata and body bytes, and compare it with the bound.}
\end{requirement}

\begin{requirement}{HLR-PERFORMANCE.LOOKUP-01}[draft][stakeholderRequirement]{Lookup latency flat with size}

  \localreqdiagram*{hlr08}{\reqid}{\reqdesc}

  WHILE the cache holds up to $10^7$ cached HTTP objects, the cache shall
  keep its 99th-percentile lookup latency no more than 25\,\% above the
  99th-percentile lookup latency it has while holding $10^4$ objects, on the
  same host under the same conditions.

  \emph{Lookup latency} is the time from the start of a cache lookup until
  the cache knows whether the request is a hit --- with the stored response
  head in hand --- or a miss; delivering the body is not part of it. ``The
  same conditions'' means the same storage device and file system, the same
  page-cache state, and the same mix of hits and misses over uniformly chosen
  keys. The bound is relative rather than absolute because absolute lookup
  latency depends mostly on the host's storage device and memory, which the
  deployment chooses; what the cache itself owes is that growing towards its
  capacity does not make every request slower. $10^7$ objects is a size a
  test host can hold; derived design targets may reach further.

  \reqdiaglink{overview}{\textit{View the domain overview.}}

  \reqexpect{deriveReqt}{REQ-EFFICIENCY.DIRSCALE-01}{Bound the number of entries
  any one directory of the on-disk layout holds, so that resolving an object's
  path costs no more with $10^7$ objects cached than with $10^4$.}
  \reqexpect{verify}{TC-PERFORMANCE.LOOKUP-01}{Verify that the 99th-percentile
  lookup latency with $10^7$ objects cached stays within this requirement's
  bound over that with $10^4$, on the same host under the same conditions.}
\end{requirement}

\begin{requirement}{HLR-PERFORMANCE.HITRATE-01}[draft][stakeholderRequirement]{Hit throughput near in-memory}

  \localreqdiagram*{hlr09}{\reqid}{\reqdesc}

  WHILE the objects it serves are resident in the host's memory, the cache
  shall serve cache hits on objects of 1~KiB to 1~MiB at a request rate of at
  least 60\,\% of the rate the same proxy reaches with the in-memory
  \texttt{MemCache} backend of \texttt{pingora-cache}, on the same host under
  the same load.

  A cache that holds more than fits in memory
  (\reqref{HLR-PERSISTENCE.CAPACITY-01}) still serves most of its hits from
  objects the host keeps in memory, since the operating system keeps the
  files it has recently read there. Serving such a hit costs a file-backed
  cache little more than the in-memory backend: the bytes come from the
  kernel's memory instead of the process's own, through a few more calls.
  The bound leaves room for those calls, but not for work that costs as much
  as the hit itself. \texttt{MemCache} is the reference
  \reqref{HLR-COMPLIANCE.RFC-01} already compares against. The \emph{request
  rate} is the number of requests completed per second; \emph{the same load}
  means the same objects, requested over the same number of concurrent
  client connections, from the same proxy configuration --- its worker
  threads included --- running on the same processors.

  The 60\,\% figure is proposed from measurements made on 22~October~2026
  with the benchmark of \reqref{TC-PERFORMANCE.HITRATE-01}: with every file
  operation on the blocking pool (\reqref{ADR-STORAGE.EXECUTOR-05}), hits ran
  at 48--62\,\% of \texttt{MemCache}; with the reads the page cache answers
  kept on the worker (\reqref{ADR-STORAGE.PAGECACHE-01}), at 69--113\,\%.

  \reqdiaglink{overview}{\textit{View the domain overview.}}

  \reqexpect{satisfy}{ADR-STORAGE.PAGECACHE-01}{Decide how a hit on an object
  resident in the page cache is served without a handoff to another thread, so
  that hits approach the in-memory backend's rate.}
  \reqexpect{verify}{TC-PERFORMANCE.HITRATE-01}{Verify that hits on objects the
  host keeps in memory, of 1 KiB to 1 MiB, run at no less than this
  requirement's share of the in-memory backend's request rate.}
\end{requirement}

\begin{requirement}{HLR-PERFORMANCE.STORERATE-01}[draft][stakeholderRequirement]{Store rate with host-crash loss}

  \localreqdiagram*{hlr10}{\reqid}{\reqdesc}

  WHERE its integrator has configured the cache to accept losing, in a host
  crash, objects it had stored, the cache shall store new objects of 4~KiB to
  64~KiB at a request rate of at least 40\,\% of the rate the same proxy
  reaches with the in-memory \texttt{MemCache} backend of
  \texttt{pingora-cache}, on the same host under the same load.

  By default the cache keeps what it has stored across a host crash or a
  power loss, as far as \reqref{HLR-PERSISTENCE.CRASHSAFE-02} lets it, and
  pays for that by waiting, for each store, until the storage device confirms
  that it holds the data. On a consumer SSD that wait limits stores to about
  a sixth of the in-memory rate. A deployment may prefer losing some of its
  objects in a host crash, and fetching them again from the origin, to
  storing at the device's pace; this configuration is for it.
  \reqref{HLR-PERSISTENCE.DURABLE-01} holds in it unchanged: a process exit
  loses nothing. \reqref{HLR-PERSISTENCE.CRASHSAFE-02} holds with the
  exception it states for this configuration: on a file system that may
  record a file's length before its data, a host crash can make the cache
  serve content that differs from what was stored, unless the integrator
  also switches on the discard \reqref{ADR-PERSISTENCE.UNSYNCED-01}
  decides. A
  store request asks for an object not cached yet, which the
  cache fetches from the origin and stores; the request rate and the same
  load are as \reqref{HLR-PERFORMANCE.HITRATE-01} defines them.

  The 40\,\% figure is proposed from measurements made on 22~October~2026
  with the benchmark of \reqref{TC-PERFORMANCE.STORERATE-01}, on a consumer
  SSD: stores ran at 15--16\,\% of \texttt{MemCache} when each waited for the
  device, and at 46--49\,\% when none did.

  \reqdiaglink{overview}{\textit{View the domain overview.}}

  \reqexpect{satisfy}{ADR-PERSISTENCE.UNSYNCED-01}{Decide the configuration
  under which stores do not wait for the storage device, and what the cache does
  with their content after a host restart.}
  \reqexpect{verify}{TC-PERFORMANCE.STORERATE-01}{Verify that, with stores
  unsynchronised, storing new objects of 4 KiB to 64 KiB runs at no less than
  this requirement's share of the in-memory backend's request rate.}
\end{requirement}

\begin{requirement}{HLR-PERFORMANCE.BURSTHITS-01}[draft][stakeholderRequirement]{Hits during a burst of stores}

  \localreqdiagram*{hlr11}{\reqid}{\reqdesc}

  WHILE it stores new objects of 1~MiB over 16 concurrent connections, each
  sending its next request as soon as its last one completes, the cache
  shall serve cache hits on objects resident in the host's memory with a
  99th-percentile latency of at most twice the 99th-percentile latency of
  the same hits with no store in progress, on the same host under the same
  load.

  A cache fills in bursts --- when it starts empty, after a purge, when a
  large object turns popular --- and serves hits all the while. The stores
  then share the proxy's processors and the host's storage device with the
  hits: each store copies its body into the operating system's page cache,
  which writes it to the device in the background and holds back the
  writers whose data outruns the device. The bound lets a hit pay for that
  sharing, but not wait behind the stores. It holds whatever the configured
  durability: a store that waits for the device
  (\reqref{HLR-PERSISTENCE.CRASHSAFE-02}) leaves less data waiting to be
  written, but its waits fall on the same processors. A store request is as
  \reqref{HLR-PERFORMANCE.STORERATE-01} defines it, and the same load as
  \reqref{HLR-PERFORMANCE.HITRATE-01} does.

  The factor of 2 is proposed from measurements made on 20~November~2026
  with the benchmark of \reqref{TC-PERFORMANCE.BURSTHITS-01}, on a consumer
  SSD under ext4 and XFS. With each store's file work on the blocking pool
  or in inline slots (\reqref{ADR-STORAGE.INLINEWRITES-02}), the hits' 99th
  percentile during the stores was 3.0 to 3.8 times its value without them
  when stores were unsynchronised, and 2.2 to 2.4 times when each waited for
  the device. With the writes past each store's first 64~KiB on an
  \texttt{io\_uring} ring (\reqref{ADR-STORAGE.IOURING-01}), it was 1.4 to
  1.7 and 1.9 times.

  \reqdiaglink{overview}{\textit{View the domain overview.}}

  \reqexpect{satisfy}{ADR-STORAGE.IOURING-01}{Decide how the writes of a burst
  of large stores are issued so that hits on objects resident in memory keep
  their tail latency within the bound.}
  \reqexpect{verify}{TC-PERFORMANCE.BURSTHITS-01}{Verify that, while objects of
  1 MiB are stored over 16 connections, hits keep their 99th-percentile latency
  within twice its value with no store in progress, with stores synchronised and
  unsynchronised alike.}
\end{requirement}

\begin{requirement}{HLR-COMPAT.PINGORA-01}[draft][stakeholderRequirement]{Compatible with Pingora}

  \localreqdiagram*{hlr03}{\reqid}{\reqdesc}

  The cache shall integrate with the \texttt{pingora-cache} 0.9 release line
  --- version 0.9.0 and its patch releases --- through only the extension
  points those releases expose publicly, without modification of the Pingora
  source.

  The \texttt{Storage} backend is the primary integration point, but
  preserving cache semantics across restarts may require additional,
  separately-configured components --- for example eviction-state coordination
  (\reqref{FRE-COMPAT.EVICTION-01}) --- which meet this requirement as long as
  they, too, use only public extension points. Verification is by inspection
  of the deliverable's dependency manifest (Pingora crates constrained to
  0.9.x, none patched or vendored) and of the interfaces it uses. A patch
  release of the 0.9 line is taken as it comes; adopting a later minor
  release is a revision of this requirement, not an implicit obligation.
  What the persisted cache owes across any Pingora change is stated in
  \reqref{FRE-COMPAT.FORMATUPGRADE-01}. This version is such a revision: it
  moves the target from 0.8.1 to the 0.9 line, whose \texttt{Storage} and
  \texttt{EvictionManager} surfaces differ in ways the requirements below name
  explicitly.

  \reqdiaglink{overview}{\textit{View the domain overview.}}

  \reqexpect{deriveReqt}{FRE-COMPAT.UNSIZED-02}{Require the backend to store a
  body whose total length is unknown until its last chunk arrives, as the miss
  handler delivers it.}
  \reqexpect{deriveReqt}{FRE-COMPAT.CONCURRENT-01}{Require several in-flight
  writes of the same key to stay isolated from each other, each durably
  published whole or not at all, and to converge on a single winner.}
  \reqexpect{deriveReqt}{FRE-COMPAT.EVICTION-01}{Require the eviction manager's
  view, once the restart procedure completes, to represent every durably
  published object once and nothing else.}
  \reqexpect{deriveReqt}{FRE-COMPAT.HOTUPGRADE-01}{Require the outgoing process
  of a hot upgrade to make no further durable change once signalled, and both
  processes to keep the shared cache consistent while they overlap.}
  \reqexpect{deriveReqt}{FRE-COMPAT.STREAMFLAG-01}{Require the backend to
  advertise streaming partial writes, which the framework's stampede protection
  assumes.}
  \reqexpect{deriveReqt}{FRE-COMPAT.STREAMING-01}{Require a lookup of a key with
  a store in flight to answer with a partial hit that streams that store's
  body.}
  \reqexpect{deriveReqt}{FRE-COMPAT.STREAMDELIVERY-02}{Require a partial hit's
  reader to deliver the bytes already written and then each chunk the store
  appends, within the stated delay.}
  \reqexpect{deriveReqt}{FRE-COMPAT.STREAMEND-01}{Require a partial hit's reader
  to deliver the remaining bytes and end the body normally when its store

  \reqexpect{deriveReqt}{FRE-COMPAT.FORMATUPGRADE-01}{Require a record written

  \reqexpect{deriveReqt}{FRE-COMPAT.WRITEFAIL-01}{Require a failure to write a

  \reqexpect{deriveReqt}{FRE-COMPAT.EXPIRE-01}{Require an expiry the framework

\begin{requirement}{HLR-COMPLIANCE.RFC-01}[draft][stakeholderRequirement]{No added RFC 9111/9110 deviation}

  \localreqdiagrams*{hlr04}{\reqid}{4}{\reqdesc}

  The cache's observable HTTP caching behaviour shall match that of the same
  proxy configured with the stock \texttt{MemCache} backend of
  \texttt{pingora-cache}, in every respect governed by RFC~9111 (\emph{HTTP Caching}) and
  RFC~9110 (\emph{HTTP Semantics}).

  \texttt{pingora-cache} applies these semantics --- freshness calculation,
  conditional revalidation, \texttt{Cache-Control} handling --- without
  claiming full conformance. This requirement therefore asks the backend to
  add no deviation of its own, not to remove the framework's. Behaviour
  observed across a process restart, which \texttt{MemCache} cannot exhibit,
  is compared against the behaviour \texttt{MemCache} shows within a single
  process run.

  \reqdiaglink{overview}{\textit{View the domain overview.}}

  \reqexpect{deriveReqt}{FRE-COMPLIANCE.HEADERS-01}{Require the backend to
  return the complete response head it was handed, status, version and every
  header field, after a restart included.}
  \reqexpect{deriveReqt}{FRE-COMPLIANCE.TRAILERS-01}{Require the backend never
  to return a trailer field as a header field.}
  \reqexpect{deriveReqt}{FRE-COMPLIANCE.BODY-01}{Require every read of a stored
  body, from its start or from a sought position, to deliver exactly the bytes
  stored.}
  \reqexpect{deriveReqt}{FRE-COMPLIANCE.FRESHNESS-01}{Require the freshness
  lifetime and current age the framework evaluates from a retrieved object to
  match those of the object as it was stored.}
  \reqexpect{deriveReqt}{FRE-COMPLIANCE.VALIDATORS-01}{Require the ETag and
  Last-Modified validator fields to be returned byte for byte in every form
  conditional revalidation depends on.}
  \reqexpect{deriveReqt}{FRE-COMPLIANCE.REVALIDATION-01}{Require a metadata
  update to replace the object's metadata and header fields while keeping its
  body unchanged under the same key.}
  \reqexpect{deriveReqt}{FRE-COMPLIANCE.METAATOMIC-01}{Require every lookup
  during a metadata update to see the whole pre-update or the whole post-update
  metadata, never a mixture.}
  \reqexpect{deriveReqt}{FRE-COMPLIANCE.METAPERSIST-01}{Require a metadata
  update reported as applied to be what a later process of the backend returns.}
  \reqexpect{deriveReqt}{FRE-COMPLIANCE.METAABSENT-01}{Require an update of a
  key that holds no object to report a distinguishable error and leave the key
  empty.}
  \reqexpect{deriveReqt}{FRE-COMPLIANCE.REPLACE-01}{Require every lookup served
  from a published object to return the object most recently published under its
  key, whole.}
  \reqexpect{deriveReqt}{FRE-COMPLIANCE.READERISOLATION-01}{Require a reader
  whose object is replaced or purged to deliver only that object's own bytes,
  ending normally or with an error.}
  \reqexpect{deriveReqt}{FRE-COMPLIANCE.VARY-01}{Require a lookup to return the
  object stored under exactly the looked-up key, primary or variant slot, or a
  miss.}
  \reqexpect{deriveReqt}{FRE-COMPLIANCE.VARYISOLATION-01}{Require a store,
  replacement, update or purge of one variant to leave every other variant of
  its primary key unchanged.}
  \reqexpect{deriveReqt}{FRE-COMPLIANCE.PURGE-01}{Require an invalidating purge
  to make the key's stored object, its in-flight stores and, for a primary key,
  its variants unservable on every later lookup.}
  \reqexpect{deriveReqt}{FRE-COMPLIANCE.PURGEABSENT-01}{Require a purge or
  expiry of a key with no stored object to report that nothing was found, with
  no error and no other change.}
  \reqexpect{deriveReqt}{FRE-COMPLIANCE.PURGEDURABLE-01}{Require the outcome of
  an invalidating purge to be reported only once the key's absence survives a
  crash or restart.}
  \reqexpect{deriveReqt}{FRE-COMPLIANCE.INCOMPLETE-02}{Require that no store
  that did not complete, or whose content had not reached stable storage where
  that matters, is ever served.}
  \reqexpect{deriveReqt}{FRE-COMPLIANCE.PARTIALABORT-01}{Require a partial hit's
  reader to end with an error, never a normal end of body, when its in-flight
  store aborts.}
  \reqexpect{verify}{TC-COMPLIANCE.RFC-02}{Verify that the file-system backend
  adds no RFC 9111/9110 deviation, by running the same caching scenarios against
  the proxy with this backend and with the stock MemCache and comparing the
  responses.}
\end{requirement}
